# PostgreSQL 인덱스 최적화 실험

## 1. 실험 목적

QueuePick 주문 목록 조회에서 PostgreSQL B-tree 인덱스의 효과를 검증한다.

인덱스 적용 전후의 실행 계획, 실행 시간, 버퍼 사용량을 비교하고 검색 범위에 따른 실행 계획의 차이를 분석한다.

## 2. 실험 환경

- Java 21 / Spring Boot 3.5.7
- PostgreSQL 17 / Testcontainers
- 주문 데이터 100,000건
- 조회 조건: 최신 주문 20건
- 측정 방식: 워밍업 3회, 본 측정 7회, 중앙값 사용
- 측정 도구: `EXPLAIN (ANALYZE, BUFFERS)`

## 3. 인덱스 적용 전후 비교

조회 SQL:

```sql
SELECT *
FROM orders
ORDER BY created_at DESC
LIMIT 20;
```

적용 인덱스:

```sql
CREATE INDEX idx_orders_created_at
ON orders (created_at DESC);
```

| 항목 | 적용 전 | 적용 후 |
|---|---|---|
| 실행 계획 | Seq Scan + Sort | Index Scan |
| 실행 시간 중앙값 | 11.636ms | 0.072ms |
| 실행 시간 비율 | 기준 | 약 161.6배 짧음 |

인덱스 적용 전에는 100,000건을 순차적으로 읽고 상위 20건을 정렬했다.

인덱스 적용 후에는 정렬된 인덱스를 이용해 필요한 20건을 조회했다.

## 4. 검색 범위에 따른 실행 계획

| 조건 | 조회 행 수 | 실행 계획 | 실행 시간 |
|---|---:|---|---:|
| 최근 1시간 | 3,597 | Index Scan | 0.524ms |
| 최근 1일 | 86,397 | Seq Scan | 10.099ms |

검색 범위가 좁을 때는 인덱스를 활용했지만, 대부분의 데이터를 조회하는 조건에서는 Seq Scan을 사용했다.

PostgreSQL의 비용 기반 옵티마이저가 데이터 분포와 예상 처리 비용을 고려해 실행 계획을 선택한다는 점을 확인했다.

## 5. 기술 선택

QueuePick의 최신 주문 목록 조회에 `created_at` B-tree 인덱스를 적용할 가치가 있다고 판단했다.

다만 실제 운영 인덱스 적용 여부는 다음 사항을 추가로 고려해야 한다.

- 주문 조회 API의 실제 검색 조건
- 데이터 증가량
- INSERT 및 UPDATE 시 인덱스 유지 비용
- 인덱스 저장 공간
- 운영 환경의 조회 빈도와 데이터 분포

## 6. 실험의 한계

이번 실험은 Testcontainers의 PostgreSQL에서 수행했다.

반복 실행에 따른 캐시 효과가 있으며, 인덱스 적용 전후를 고정된 순서로 측정했다.

또한 `EXPLAIN ANALYZE` 계측 비용이 포함되어 있어 실제 API 응답 시간을 나타내지는 않는다.

따라서 측정 결과를 모든 환경에서 동일하게 재현되는 성능 향상률로 일반화하지 않는다.
