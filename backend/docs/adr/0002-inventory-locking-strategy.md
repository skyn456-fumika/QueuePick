# ADR-0002: 한정 수량 상품의 재고 차감에 비관적 락을 우선 사용한다

- 상태: 채택 (추가 검증 필요)
- 결정일: 2026-10-28
- 관련 문서: `docs/performance/inventory-contention-benchmark.md`

## 1. 배경

QueuePick은 한정 수량 상품에 다수의 주문 요청이 집중될 수 있는 서비스다.

재고 차감 과정에서 다음 요구사항을 충족해야 한다.

- 초과 판매 방지
- 재고 정합성 보장
- 동시 주문 처리
- 높은 주문 성공률
- 장애 및 예외 발생 시 트랜잭션 롤백

## 2. 검토한 대안

### 대안 A: 낙관적 락

JPA `@Version`으로 동시 수정 충돌을 감지한다.

장점:

- 조회 시 별도 행 잠금을 요청하지 않음
- 충돌이 드문 환경에서 활용 가능

단점:

- 고경합 환경에서 충돌 실패가 빈번함
- 성공률 개선을 위한 재시도 정책이 필요할 수 있음

### 대안 B: 낙관적 락 + 재시도

낙관적 락 충돌 발생 시 새로운 트랜잭션에서 제한된 횟수만큼 재시도한다.

장점:

- 주문 성공률 개선 가능
- 일시적인 충돌에 대응 가능

단점:

- DB 재조회와 트랜잭션 재실행 비용
- 재시도 대기 시간 증가
- 최대 재시도 횟수 초과 시 최종 실패

### 대안 C: 비관적 락

JPA `PESSIMISTIC_WRITE`를 사용해 재고 조회 시 DB 행 잠금을 획득한다.

장점:

- 동일 재고에 대한 수정 경쟁을 순차적으로 처리
- 별도 애플리케이션 재시도 없이 높은 성공률 확보 가능

단점:

- 잠금 대기 시간 발생
- 커넥션 점유 시간 증가 가능
- 락 타임아웃 및 데드락 고려 필요

## 3. 결정

현재 QueuePick의 한정 수량 상품 재고 차감에는 비관적 락을 우선 적용한다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("""
    SELECT i
    FROM Inventory i
    WHERE i.product.id = :productId
    """)
Optional<Inventory> findByProductIdWithLock(
        @Param("productId") Long productId
);
```

실제 PostgreSQL 환경에서는 `FOR NO KEY UPDATE` 형태의 행 잠금 SQL이 실행되는 것을 확인했다.

## 4. 선택 근거

동시 주문 10건이 하나의 상품에 집중되는 조건에서 7회 반복 측정한 결과:

| 방식 | 성공률 | 전체 시간 중앙값 |
|---|---:|---:|
| 낙관적 락 | 10% | 25.83ms |
| 낙관적 락 + 재시도 | 95.71% | 181.29ms |
| 비관적 락 | 100% | 45.45ms |

현재 테스트 조건에서는 비관적 락이 재시도 방식보다 높은 성공률과 짧은 전체 소요 시간을 보였다.

## 5. 결정의 영향

- 재고 차감 트랜잭션에서 DB 행 잠금을 사용한다.
- 트랜잭션 범위를 불필요하게 길게 유지하지 않는다.
- 외부 API 호출 등 오래 걸리는 작업을 락 보유 구간에 포함하지 않는다.
- 향후 락 대기 시간과 타임아웃을 관측할 수 있도록 개선한다.
- `@Version`은 유지하며 엔티티 변경 충돌 검증에도 활용한다.

## 6. 재검토 조건

다음 상황에서는 전략을 다시 평가한다.

- 동시 요청 수가 크게 증가하는 경우
- DB 커넥션 풀이 고갈되는 경우
- 잠금 대기 시간이 허용 수준을 초과하는 경우
- 락 타임아웃 또는 데드락이 빈번한 경우
- 여러 서버 인스턴스로 확장하는 경우

## 7. 결론

현재 실험에서는 비관적 락이 한정 수량 상품의 고경합 주문 처리에 적합한 선택으로 나타났다.

다만 이 결정은 현재 측정 환경과 비즈니스 요구사항을 기준으로 한 것이며, 트래픽 증가와 운영 환경 변화에 따라 재검토한다.
