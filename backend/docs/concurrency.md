# 재고 동시성 제어 — 낙관적 락

## 1. 문제 상황

한정 수량 상품에 여러 사용자가 동시에 주문하는 상황에서 재고 정합성을 보장해야 한다.

예를 들어 재고가 1개일 때 두 사용자가 동시에 주문하면, 성공한 재고 차감은 최대 1건이어야 한다.

### 요구사항

- 재고 수량은 음수가 될 수 없다.
- 동일한 재고에 대한 동시 수정 충돌을 감지해야 한다.
- 충돌한 트랜잭션의 변경 사항은 롤백되어야 한다.
- 최종 재고 수량은 성공한 차감 횟수와 일치해야 한다.

## 2. 적용한 해결 방법

JPA의 `@Version`을 이용한 낙관적 락을 적용했다.

```java
@Version
private long version;
```

Hibernate는 엔티티를 수정할 때 기존 버전을 UPDATE 조건에 포함한다.

```sql
-- 실제 SQL 로그가 아닌 동작 원리를 설명하기 위한 예시
UPDATE inventories
SET available_quantity = 0,
    version = 1
WHERE id = 1
  AND version = 0;
```

동일한 버전을 조회한 다른 트랜잭션이 먼저 수정했다면, UPDATE 대상 행이 없어지므로 낙관적 락 충돌이 발생한다.

## 3. 테스트 방법

기술 스택:

- Java 21
- Spring Boot 3.5.7
- Spring Data JPA / Hibernate
- PostgreSQL 17
- Testcontainers
- JUnit 5

### 테스트 시나리오 A: 동시 주문

1. 초기 재고를 1개로 설정한다.
2. `ExecutorService`로 두 개의 주문 작업을 생성한다.
3. `CountDownLatch`를 이용해 두 작업의 시작 시점을 맞춘다.
4. 주문 성공 수, 저장된 주문 수, 최종 재고를 검증한다.

### 테스트 시나리오 B: 동일 버전 충돌

1. 각 트랜잭션에서 동일한 재고를 조회한다.
2. 두 트랜잭션이 조회를 완료할 때까지 기다린다.
3. `CountDownLatch`로 수정 작업을 시작한다.
4. `EntityManager.flush()`로 UPDATE를 실행한다.
5. 낙관적 락 충돌 및 최종 데이터 상태를 검증한다.

## 4. 테스트 결과

| 항목 | 결과 |
|---|---|
| 초기 재고 | 1개 |
| 동시 작업 | 2개 |
| 성공한 재고 차감 | 1건 |
| 실패한 재고 차감 | 1건 |
| 최종 재고 | 0개 |
| 최종 버전 | 1 |
| 발생한 충돌 예외 | `OptimisticLockException` |
| 테스트 결과 | PASS |

두 트랜잭션이 동일한 버전을 수정하려는 상황에서 한 트랜잭션만 성공하고 다른 트랜잭션에서는 낙관적 락 충돌이 발생하는 것을 확인했다.

## 5. 기술적 판단과 한계

낙관적 락은 충돌 가능성이 상대적으로 낮은 환경에서 유용한 선택지가 될 수 있다.

다만 충돌이 빈번한 환경에서는 실패 및 재시도 비용이 증가할 수 있다.

현재 검증한 것은 데이터 정합성과 버전 충돌 감지이며, 높은 동시성 환경에서의 성능 우위까지 검증한 것은 아니다.

### 향후 검증할 내용

- 비관적 락과 비교
- 충돌 빈도에 따른 처리량 및 응답 시간
- 낙관적 락 재시도 정책
- 대량 동시 주문 시 성능 측정
- 사용자에게 반환할 충돌 응답 설계

## 6. 결론

JPA의 `@Version`을 이용해 동일 데이터에 대한 동시 수정 충돌을 감지할 수 있음을 실제 PostgreSQL 통합 테스트로 확인했다.

향후 비관적 락과 조건부 UPDATE 방식도 동일한 조건에서 비교해 재고 차감에 적합한 전략을 결정할 예정이다.

## 비관적 락 검증

### 적용 방식
JPA의 PESSIMISTIC_WRITE 사용

### 실제 PostgreSQL SQL
SELECT ... FOR NO KEY UPDATE

- 초기 재고: 1개
- 동시 주문: 2건

### 검증 결과
- 성공 주문: 1건
- 실패 주문: 1건

### 확인한 특징
- 재고 조회 시 DB 행 잠금 획득
- 동시 수정 요청은 잠금 해제까지 대기
- 기존 @Version을 통한 버전 검사도 유지
